# MCP 2026-07-28: what this server must and should implement

Sources: <https://modelcontextprotocol.io/specification/2026-07-28> and all its
sub-pages, `schema/2026-07-28/schema.ts`, and the
`io.modelcontextprotocol/tasks` extension spec. Verified on 2026-09-04. The
official Rust SDK `rmcp` 3.x implements this revision. It is SEP-1730 Tier 1
conformant on 2026-07-28 and on 2025-11-25.

## The one thing to internalize

2026-07-28 is a stateless rewrite, and it breaks compatibility. These things are
gone: the `initialize` handshake, the session ID, the HTTP GET stream, the
server-initiated JSON-RPC requests, `ping`, `logging/setLevel`, and
`resources/subscribe`. Each request carries the protocol version and the client
capabilities in `_meta`. Servers MUST implement `server/discover`. The
server-to-client interactions are elicitation, sampling, and roots. To do one,
the server returns `resultType: "input_required"`, and the client retries with
`inputResponses`. This mechanism is Multi Round-Trip Requests (MRTR). Roots,
Sampling, and Logging are deprecated. Tasks moved to an extension.

The spec calls the revisions before 2026 "legacy". A server may serve both eras.
An `initialize` request means legacy semantics. A request that carries `_meta`
means modern semantics. rmcp does this automatically.

## Mandatory baseline (not capabilities)

- `server/discover`: returns `supportedVersions`, `capabilities`, `_meta.io.modelcontextprotocol/serverInfo`, and the required `ttlMs` and `cacheScope`. `instructions` is optional.
- Validate the `_meta` of each request. `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` are required. A missing key gives `-32602`. An unsupported version gives `-32022` with `data.supported`. A need for an undeclared client capability gives `-32021`.
- Put `resultType` on every result. The value is `complete`, `input_required`, or `task`.
- Every result SHOULD carry `_meta.io.modelcontextprotocol/serverInfo`.
- Statelessness: a server MUST NOT rely on prior requests on the same connection. Explicit identifiers reference the state across requests, and they pass as ordinary arguments.

## Server capabilities and what we do with each

| Capability | Decision | Notes |
|---|---|---|
| `tools` `{listChanged: false}` | Yes | The tool set is static for each process. The order is deterministic, which helps the prompt-cache hit rate. `tools/list` must carry `ttlMs` and `cacheScope`. |
| Tool `outputSchema` + `structuredContent` | Yes, every tool | Use any JSON Schema 2020-12. Also serialize the same payload into a text block. |
| Tool `annotations` | Yes, all five on every tool | The defaults are `readOnlyHint` false, `destructiveHint` true, `idempotentHint` false, and `openWorldHint` true. An omission is a silent gap. Enforce the annotations by test. |
| `resource_link` content blocks | Yes | A tool result links to a `dms://snitch/{token}` resource. |
| `resources` `{listChanged: false, subscribe: false}` | Yes | Implement `resources/list`, `resources/templates/list`, and `resources/read`. Not-found is `-32602`. Use `cacheScope: "private"` for anything derived from the user's account. |
| `completions` | Yes | Use them only for the prompt arguments and the resource-template variables, which are token and tag. Do not use them for the tool arguments. |
| `prompts` `{listChanged: false}` | Yes | Two or three prompts. The arguments are strings. |
| Elicitation (client capability, form mode) | Yes, via MRTR | Confirm before `delete_snitch`. Use a flat object schema of primitives. A server MUST NOT request secrets through a form. Handle a decline and a cancel. Use it only when the client declares `elicitation.form`. |
| Progress (`_meta.progressToken`) | Where cheap | Nothing here is long-running. Skip it unless a fan-out appears. |
| Cache hints (`ttlMs`, `cacheScope`) | Yes | Required on `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, and `resources/read`. |
| Icons | Yes | Put them on serverInfo and on the tools. Use an `https` URI or a `data:` URI. |
| `extensions` `io.modelcontextprotocol/tasks` | No | There are no long-running operations. Revisit this only if a "wait for next check-in" tool ever exists. |
| `subscriptions/listen` | No | It would require polling DMS for the status changes. Advertise the `resources: {}` semantics accordingly. |
| `logging` | No | Deprecated (SEP-2577). Log to stderr on stdio. |
| Sampling, Roots | No | Deprecated. |
| `x-mcp-header` (SEP-2243) | No | It is for routing only. It is irrelevant for a single-tenant wrapper. |

## Error policy (spec plus rmcp README rule)

- A protocol error becomes a JSON-RPC error, such as `-32602`. The protocol errors are an unknown tool, malformed params, and a missing `_meta`.
- A tool execution error becomes a result with `isError: true`, so that the model can self-correct. It is never a JSON-RPC error. These errors are an upstream 4xx or 5xx, a validation that the API rejects, and a rate limit.
- Error code allocation: `-32000..-32019` are implementation-defined. `-32020..-32099` are reserved for the spec.

## Transport rules

### stdio (primary)

- Write one JSON-RPC message per line, in UTF-8, with no embedded newlines. Write nothing to stdout except the MCP messages. Anything may go to stderr.
- There are no server-initiated requests. The server writes responses and notifications only.
- Cancellation: the client sends `notifications/cancelled {requestId}`. The server stops and sends nothing further for that request.
- Shutdown: the client closes stdin. The server SHOULD exit promptly on EOF.
- The process is not a session. Clients may interleave unrelated conversations. Do not keep per-conversation memory.
- The credentials come from the environment. The spec says that a stdio server SHOULD NOT implement the OAuth authorization flow.

### Streamable HTTP (secondary; required for the official conformance suite's server mode)

- One endpoint, POST only. GET and DELETE return 405. There is no `Mcp-Session-Id`. There is no resumability, so a broken stream loses the request.
- Every POST requires the headers `MCP-Protocol-Version` and `Mcp-Method`. `tools/call`, `resources/read`, and `prompts/get` also require `Mcp-Name`. A mismatch gives HTTP 400 with `-32020`.
- The client sends `Accept: application/json, text/event-stream`. The server answers with JSON, or with a request-scoped SSE stream that ends in the final response.
- The server MUST validate the Origin, and it returns 403 on a failure. Local servers SHOULD bind 127.0.0.1 only.
- When the client closes the SSE stream, that is a cancellation.
- Token passthrough is forbidden. The MCP-side credential and the DMS-side credential must be separate. Do not accept the raw DMS key as the bearer token, and do not forward it.
- For per-user DMS keys, the sanctioned pattern is URL-mode elicitation. That pattern is out of scope for the first release. HTTP mode is single-tenant. It takes the key from the environment and uses a separate caller bearer token.

## Reserved `_meta` keys

These keys are reserved: `progressToken`,
`io.modelcontextprotocol/{protocolVersion, clientInfo, clientCapabilities, logLevel, subscriptionId, serverInfo}`,
`traceparent`, `tracestate`, and `baggage`. Any prefix whose second label is
`modelcontextprotocol` or `mcp` is also reserved. Our own keys use a reverse-DNS
prefix.

## Changelog highlights relevant to us

- 2026-07-28: the stateless protocol, `server/discover`, MRTR, `subscriptions/listen`, `resultType`, the cache hints, the required HTTP headers, the extensions map, and the tasks extension. It deprecates roots, sampling, and logging. It renumbers resource-not-found to `-32602`.
- 2025-11-25: icons, URL-mode elicitation, and titled enums in elicitation. An input validation error is a tool-execution error, not a protocol error. JSON Schema 2020-12 is the default dialect. The tool-name guidance is 1 to 128 characters from `[A-Za-z0-9_.-]`.
- 2025-06-18: `structuredContent` and `outputSchema`, `resource_link`, elicitation, and a `title` that is distinct from `name`. It removes batching.

## Testing tools

- `modelcontextprotocol/conformance`: run `npx @modelcontextprotocol/conformance server --url http://127.0.0.1:PORT/mcp --suite all --spec-version 2026-07-28 --expected-failures baseline.yaml`. Server mode requires Streamable HTTP. A reusable GitHub Action exists, and rmcp's own `conformance.yml` is the recipe.
- `modelcontextprotocol/inspector` CLI: run `npx @modelcontextprotocol/inspector --cli ./target/debug/mcp-deadmansnitch --method tools/list --strict`. It works over stdio. `--strict` lints the tool schemas for portability.
- The rmcp in-process client over `tokio::io::duplex` gives fast tool-level tests. `TokioChildProcess` against `CARGO_BIN_EXE_*` gives contract tests on the real binary.
